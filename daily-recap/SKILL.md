# daily-recap

Задача: за пару минут дать человеку — в том числе новичку, который не знает нашей кухни — картину,
чем занимались в проектах за прошедший период. Не список коммитов, а рассказ: что и зачем поменялось,
что уже в деле, что ещё в работе.

---

## 0. Явное указание побеждает всё

Если в запросе **названы срок и/или репозиторий** — отчёт ровно за этот срок и ровно по этим
репозиториям, ничего сверх:

| Запрос | Период | Репозитории |
|---|---|---|
| «чем вчера занимались» | вчера 10:00 → сейчас (§2) | все три |
| «что делали в консилиуме за неделю» | последние 7 дней → сейчас | только консилиум |
| «что влили в бэкенд в пятницу» | пятница 00:00 → 23:59 | только бэкенд |
| «что было в админке с понедельника» | понедельник 00:00 → сейчас | только админка |
| «чем занимались с пятницы» (в понедельник) | пятница 10:00 → сейчас | все три |

Не дописывать «а ещё в других репозиториях было…» и не расширять срок «для полноты». Не спрашивать
«точно только этот?» — названное и есть ответ. В шапке отчёта так и писать: «по просьбе: консилиум,
последние 7 дней».

## 1. Репозитории

Обходить всегда все три, в этом порядке. Пути указаны для основной машины; на другой машине
сначала проверить `ls`, если не нашлось — спросить путь один раз, не гадать.

| Название в отчёте | Путь (Git Bash) | GitHub |
|---|---|---|
| Бэкенд (сайт и API, Laravel) | `/c/work/eastclinic/BackendLaravel` | `eastclinic-team/BackendLaravel` |
| Админка | `/c/work/eastclinic/diqi` | `eastclinic-team/AdminPanel` |
| Консилиум | `/c/work/consilium` | `jeromwork/consilium` |

Если названы другие репозитории или только один — брать названные (§0). Соседние каталоги
(`consilium-wt`, `BackendLaravel-cache`, `Laravel2` и т.п.) — это worktree и копии, их не обходить.

## 2. Период

Два варианта, третьего нет:

1. **Пользователь назвал период** («с пятницы», «за сегодня», «за прошлую неделю», «с 10 утра
   вчера», «за 8–9 сентября») — брать его. Конец периода — сейчас, если не сказано иное.
   Названа только дата без времени — начало дня 00:00.
2. **Не назвал — со вчерашних 10:00 до сейчас.** Никакой памяти о прошлых вызовах скил не хранит:
   после выходных владелец сам скажет «с пятницы».

Границы по умолчанию получать скриптом, а не считать в голове:

```bash
~/.claude/skills/daily-recap/scripts/recap.sh window
# SINCE=2026-09-10T10:00:00
# UNTIL=2026-09-11T08:37:29
```

Для явно названного периода — посчитать `SINCE`/`UNTIL` в том же формате `YYYY-MM-DDTHH:MM:SS`
(`date -d "last friday 10:00" +%Y-%m-%dT%H:%M:%S` и т.п.). В шапке отчёта обязательно написать,
какой период взят и почему («по умолчанию: 10.09 10:00 → 11.09 08:37» / «по просьбе: с пятницы»).

## 3. Сбор фактов

По каждому репозиторию — один вызов сборщика, ничего руками не изобретать:

```bash
S=~/.claude/skills/daily-recap/scripts/recap.sh
$S collect /c/work/eastclinic/BackendLaravel "$SINCE" "$UNTIL"
$S collect /c/work/eastclinic/diqi          "$SINCE" "$UNTIL"
$S collect /c/work/consilium                "$SINCE" "$UNTIL"
```

Скрипт делает `git fetch` (чтобы увидеть ветки, запушенные с другой машины) и печатает:

- текущую ветку, **незакоммиченные правки и stash** — это «работа прямо сейчас», даты у неё нет;
- **ветки, на которых были коммиты в период** — локальные и удалённые, с автором;
- **коммиты в период на всех ветках**, новые сверху, с полным описанием, списком веток, где коммит
  лежит (`-> origin/main` = уже влит; только фичевая ветка = ещё в работе), и списком файлов;
  merge-коммиты помечены `(MERGE)` — это не отдельная работа, а момент вливания;
- **незапушенная работа** — локальные ветки с коммитами за период, которых нет ни на одной
  удалённой ветке: это работа, которой GitHub ещё не видел. Обязательно в отчёт, статус 🛠;
- **планы и документы**, тронутые за период (`docs/tasks/*.md`, `*plan*`, `*handoff*`, `*todo*` —
  закоммиченные и незакоммиченные) с оглавлением и счётчиком чекбоксов;
- **pull requests**, менявшиеся в период: `[OPEN]` — на проверке, `[MERGED]` — принят, `[CLOSED]` —
  отклонён. Время у PR в UTC (на 3 часа меньше московского).

### Планы — читать, а не только перечислять

Если за период появился или менялся план, он для отчёта важнее отдельных коммитов: это и есть
«чем занимаемся». Прочитать документ целиком (`Read`), и в отчёте дать по нему отдельный блок:

- о чём план в двух предложениях простыми словами;
- **что из него уже сделано** — сверить пункты/очереди плана с коммитами и PR за период (заголовок
  PR часто прямо называет пункт: «Очередь 13», «T36»);
- **что в работе сейчас** — ветки без PR, незапушенные коммиты, незакоммиченные правки, которые
  ложатся на пункт плана;
- **что дальше** — ближайшие невыполненные пункты, как они названы в плане; секцию «отложено»
  упомянуть одной строкой.

Чекбоксы `[x]/[ ]` — если есть, брать их; если план прозой (очереди, волны, задачи Txx) —
статус выводить из PR/коммитов, а не выдумывать. Не уверен, сделан ли пункт — писать «по коммитам
не видно», не «сделано».

Читать описания коммитов целиком — в этих репозиториях они уже написаны как объяснение «что было не
так и что стало». Если из описания не понятно, что изменилось для людей, — посмотреть diff
(`git -C <repo> show <sha>`) или тело PR (`gh pr view <n> --repo <owner/repo>`), но в отчёт команды
не тащить.

Статус каждой задачи определять так:

| Признак | Статус |
|---|---|
| коммит лежит в `origin/main` / PR `[MERGED]` | ✅ **влито** — уже в основной ветке, поедет на прод со следующей выкаткой |
| PR `[OPEN]` | 🔍 **на проверке** — работа готова, ждёт ревью/слияния |
| коммиты только на фичевой ветке, PR нет (в т.ч. ветка ещё не запушена) | 🛠 **в работе** |
| только `git status` / stash | ✏️ **не сохранено в git** — правки лежат на диске |

## 3а. Работа вне git — то, что владелец надиктовал

Часть работы в git не попадает: ручные проверки на проде, разбор с коллегами в чатах, действия в
админке или в сторонних системах, решения. Владелец передаёт это словами — часто голосом через
распознавание, поэтому текст приходит с оговорками, повторами, «бм», самопоправками и ошибками
распознавания («гидхаб», «дите», «стил»). Это тоже отчёт, и он входит в тот же документ.

Как обрабатывать:

- **Вычистить речь, сохранить смысл.** Убрать заикания, повторы, вводные; при самопоправке брать
  последнюю версию сказанного; опечатки распознавания читать по контексту (GitHub, git, скил, фид).
- **Ничего не добавлять сверх сказанного.** «Проверял фиды» → «Проверка фида» — без того, какой
  фид и что нашлось, если владелец этого не сказал. Не додумывать результат, причину, коллег.
- **Разложить на пункты** — один пункт на одно дело: что делал; с кем / где, если сказано;
  чем закончилось и что дальше, если сказано. Статусы те же: ✅ сделано, 🛠 продолжается —
  только когда из слов ясно; не ясно — без значка.
- **Разложить по репозиториям.** Если дело явно про один из проектов (фид, страницы врачей —
  бэкенд; таблица услуг — админка; протоколы — консилиум) — пунктом в раздел этого проекта,
  с пометкой _(вне git)_. Не относится ни к одному или общее — в отдельный раздел
  «Вне кода: проверки, обсуждения, решения».
- **Тот же простой язык**, что и для коммитов: что изменилось или что проверено для людей.
- **Не понял фрагмент — не гадать.** Написать пункт как понял с пометкой «(понял так: …)», и после
  отчёта одной строкой спросить именно про этот фрагмент. Отчёт из-за этого не задерживать.

Если в запросе надиктованного нет — не спрашивать «а было ли что-то вне git?»; в конце отчёта
допускается одна строка: «Было что-то вне git — скажи, добавлю».

Пример. Надиктовано:
> ну вот вчера ещё смотрел э фиды проверял как работают ну колдунщик яндекса там бм с Сашей
> обсуждали возвраты то есть заявление на возврат как оно в портал должно уходить ну и
> ещё на проде руками поправил у врача Иванова цену ну там задвоилась

В отчёте:
> **Бэкенд** … · ✅ Проверка фида для колдунщика Яндекса — как отдаётся. _(вне git)_
> · Ручная правка на проде: у врача Иванова убрана задвоившаяся цена. _(вне git)_
> **Вне кода** · Обсуждение с Сашей: как заявление на возврат должно уходить в портал.

## 4. Отчёт

Отчёт печатается **в чат и только в чат** — владелец читает его прямо здесь. Никаких файлов,
артефактов, страниц, ссылок «посмотреть красиво» — даже если отчёт длинный. В файл — только по
явной просьбе («запиши в файл», «положи в docs/»).

### Структура

```
# Чем занимались: <период словами, напр. «среда 10.09 с 10:00 → четверг 11.09 утро»>
_Период: по умолчанию (вчера 10:00 → сейчас) / по просьбе. Репозитории: бэкенд, админка, консилиум._

**Коротко:** самая читаемая часть — многие остановятся на ней и дальше не пойдут. Поэтому не
2 предложения, а **по абзацу на каждый репозиторий, где что-то было**, и в абзаце **названа каждая
крупная задача** (одной фразой «что изменилось для людей») со статусом. Если в репозитории был
план или большая волна — перечислить, что из неё сделано, а не «выполнена почти вся». Обычный
объём — 8–15 строк. Надиктованная работа вне git входит в «Коротко» наравне с коммитами.
Подробности, примеры и номера PR — ниже, в разделах.

## Бэкенд (сайт и API)
- ✅ **<задача одной фразой — что изменилось для людей>.** 1–3 предложения: что было не так,
  что стало. _(ветка `j_...`, PR #1060)_
- 🛠 **<...>** — что делается и что осталось.
- ✏️ Не сохранено в git: <файлы одной строкой>, если есть.

## Админка
...

## Консилиум
- 📋 **План «<название>»** — о чём; сделано: …; в работе: …; дальше: …  (если план тронут за период)
- ✅ / 🛠 задачи как выше

## Вне кода: проверки, обсуждения, решения
- <пункты из надиктованного, не привязанные к одному проекту>  (раздел — только если владелец
  что-то передал; привязанное к проекту идёт в раздел проекта с пометкой _(вне git)_)

## Коллеги
- Влиты работы других авторов: <одна строка на PR/автора>.  (раздел — только если такие есть)
```

Задача ≈ ветка (или PR). Несколько коммитов одной ветки — это **одна** задача, не перечислять их
по одному. Коммит + его merge-коммит — тоже одна задача. Пустой репозиторий — одна строка
«в этом репозитории за период ничего не менялось», раздел не раздувать.

### Язык — главное правило

Читает человек, который может не знать ни Laravel, ни что такое ветка. Поэтому:

- Каждая задача — **что стало по-другому для пациента / менеджера / администратора / сайта**, а не
  какой класс тронут. Имена файлов, классов, методов, таблиц в основном тексте не нужны — если
  очень надо, в курсив в скобках в конце.
- Технический термин — только когда без него никак, и тогда сразу пояснение в скобках:
  «кэш (сохранённая копия страницы, чтобы отдавать её быстрее)».
- Слова «рефакторинг», «DTO», «миграция», «эндпоинт», «инвалидация», «идемпотентный», «проекция» —
  переводить: «переделали внутри без изменения поведения», «правила приёма данных», «изменение
  структуры базы», «адрес, по которому сайт запрашивает данные», «сброс сохранённой копии»,
  «повторный запуск ничего не ломает», «заранее посчитанная таблица».
- Один-два конкретных примера из описаний коммитов (врач такой-то, страница такая-то, цена такая-то)
  делают отчёт понятнее любого обобщения — оставлять их.
- Не оценивать («отлично поработали»), не додумывать причин, которых нет в коммитах.

Плохо:
> Рефакторинг `DoctorServiceAction`: запись переведена на `DoctorServiceOffersService::updateBinding()`,
> добавлен `assertAddressFree()`.

Хорошо:
> ✅ **Починили задвоение услуг у врача в админке.** Когда менеджер менял вариант цены у уже
> привязанной услуги, система вместо правки заводила вторую такую же строку со старой ценой — так
> у врача 1261 появилось две «Консультации». Теперь правится ровно та строка, которую редактировали,
> и вторая появиться не может. _(ветка `j_doctor_services_put_by_id_10_09_26`, PR #1060)_

Блок «Коротко» — плохо (читатель не узнает, что именно сделано):
> В бэкенде и админке закрыли историю с задвоением услуг, в консилиуме большой день по плану
> конвейера протоколов.

Хорошо:
> **Бэкенд:** влиты две правки — правка услуги врача в админке больше не заводит вторую строку
> (задвоение «Консультации» у врача 1261), и врач с единственным приёмом через полтора месяца
> перестал обгонять в списке тех, у кого приём завтра.
> **Админка:** влиты две правки с той же историей задвоения — редактор цен шлёт только цены, и
> правка цены в ячейке не переподбирает молча вариант врача (ложная скидка «~~3000~~ 2501»).
> **Консилиум:** написан и за сутки выполнен план «Конвейер протоколов» из 12 очередей: разбор
> отвязан от протокола, схлопнуты 6231 дубль, анализы читает код, у каждого признака появился
> вопрос (542 → 0 без вопроса), приёмы раскладываются в счётчики с «почему», непроверенное врачом
> в расчёт не идёт. Отдельно влиты три починки разбора (копии находок, обрыв ответа, новые
> протоколы не попадали в очередь). На проверке ждут владельца: классификатор МКБ-10 целиком
> (PR #67) и удаление 300 выдуманных протоколов из боевой базы (PR #68).

## 5. Ловушки

- **Rebase меняет дату коммита.** Старая работа, перебазированная вчера, покажется вчерашней.
  Если по описанию видно, что задача давняя, — так и написать («перенесли на свежую основу»).
- **`git fetch` без сети не сработает** — скрипт предупредит; тогда ветки с другой машины не видны,
  сказать об этом в отчёте одной строкой.
- **Незакоммиченные правки без даты.** Видно только «что лежит сейчас»; могли лежать и неделю.
  Писать «лежат правки», не «вчера правили».
- **Stash «WIP on main» полугодовой давности** — не работа за период, не упоминать.
- **Время PR в UTC.** Слитый в 05:32Z — это 08:32 по Москве; при пограничных случаях смотреть
  на локальное время коммита, а не PR.
- **«Незапушенный» коммит, чей PR уже `[MERGED]`.** Сквош-слияние на GitHub даёт новый хеш, и
  локальный коммит формально «нет ни на одной удалённой ветке». Если у ветки есть влитый PR с тем же
  названием — это не незапушенная работа, статус ✅.
- **Ветка ушла в `origin/main`, а PR не найден** — значит влито без PR или PR старше 60 последних;
  статус всё равно «влито».
